# Orders

**SPEC/program** — Order types, validation, and resolution. Reference: [movement.md](movement.md), [civilian-units.md](../game/civilian-units.md), [military-units.md](../game/military-units.md), [military-armies.md](../game/military-armies.md), [world-model-identity.md](../game/world-model-identity.md).

**Province identity:** Province ids in order payloads (e.g. destination province, spawn province, tile keys) use the **prefixed** form `regionId|localId` and must be resolved per [world-model-identity.md](../game/world-model-identity.md). Do not use bare province ids for lookup.

**Implementation (structure, not extra rules):** Work-order **visibility** checks use a target→handler map in `order_visibility.dart`. **Work-order application** on the build/work phase uses the canonical `workOrderHandlersByTarget` map in `colonizethis_logic` `lib/src/orders/work_handlers/work_order_handler_registry.dart` (one `WorkOrderHandler` per work target string; standard multi-turn build targets use `StandardBuildWorkOrderHandler`). `orders_application_work_phase.dart` resolves handlers by target lookup only — no linear handler list or `switch` on work target strings in `standard_work_handler.dart`. The repo-lint rule `repo.logic_work_target_switch` (`SPEC/program/repo-lint.md`) enforces this structurally: any `switch` statement or expression in `lib/src/orders/work_handlers/` or `lib/src/orders/order_visibility.dart` whose case patterns enumerate three or more `kWorkTarget*` constants is rejected; new dispatch entries must extend `workOrderHandlersByTarget` / `_workOrderVisibilityByTarget` (Refs #2560). Behavior matches the per-target rules below; refactors must preserve the same outcomes as existing tests. **Economy projection:** pending build and material-backed work costs in the economy preview pipeline use the same afford/deduct helpers as validation and application via `ProjectedCostEngine` in `colonizethis_logic` (work stockpile costs and `canAffordBuild` / build deduction), so preview stockpile deltas stay aligned with order submission and resolution.

## Order Types (Current Scope)

- **MoveOrder** — **Civilian only:** unit id + `destinationTileKey` (format `regionId|localProvinceId|x|y`). The enclosing destination province is derived from `destinationTileKey`. Civilian move legality is tile-scoped and uses shared occupancy rules (tile-level control override first, then province-derived control) from `civilianMayOccupyLandTileKey` (see [movement.md](movement.md) § Civilian tile moves). Civilian move validation/suggestions do **not** use map-topology adjacency. Applied in movement phase. **Land military does not use MoveOrder**; use **ArmyMoveOrder**.
- **ArmyMoveOrder** — **Army id**, destination province id. Valid if: the army exists, is owned by the ordering player, is **not** the player’s **Home Army** ([military-armies.md](../game/military-armies.md)) unless the destination is the **same** capital province (no-op or reject per TDD); destination province exists; same movement ownership/adjacency rules as former military `MoveOrder` (including **declare war** in the same-turn diplomatic draft when attacking a GP / Minor / Tribe province without an existing war — see `ArmyMoveValidator`). On apply, every regiment id in the army updates to the destination province and the army’s stationed province updates. Applied in movement phase.
- **Move army UI (shell):** The Military Units **Move** dialog must only offer destinations that pass **full** `OrderEngine` validation for the human player’s **current** draft (after any UI-driven **declare war** appended for invasion). **`AppEventHandlerScope`** must **reject** (no silent commit) an `ArmyMoveRequestedEvent` whose merged draft fails validation: log at **error**, user-visible **`ShowSnackBarEvent`**, **assert** in debug builds.
- **Civilian work upsert UI (shell):** When the human shell commits a pending civilian `WorkOrder` via `UpsertPendingCivilianWorkOrderRequestedEvent`, **`AppEventHandlerScope`** must run **one** authoritative `OrderEngine.validatePlayerOrdersWithContext` pass on the **merged** human draft (same pattern as army move validation) and **reject** (no silent commit) when any result is rejected: log at **error**, user-visible **`ShowSnackBarEvent`**, **assert** in debug builds. Layer A availability remains cheap; this is Layer B drift/race protection (Refs #2133).
- **BuildUnitOrder** — Unit type (civilian, military, or naval), optional spawn province. Validation and resolution branch on unit type category (derived from catalogs). **Spawn province semantics (current phase):** For **civilian** builds, spawn tile is always the ordering player `capitalTile` exactly (tile-exact semantics); `spawnProvinceId` may be provided but does not change civilian placement. If a civilian build is requested and the player has no resolvable `capitalTile`, the System rejects/fails with an explicit capital-tile-missing reason and performs no fallback placement. **Military:** new regiment is added to the player’s **Home Army** at the capital province (spawn province field ignored for placement unless TDD extends location choice); Home Army must exist. For naval builds, `spawnProvinceId` is ignored and spawn is always the player's home fleet at capital port. If the player has no capital province, military/naval build order is rejected per existing rules. **Civilian:** valid if player has sufficient treasury (cash) and stockpile (paper) per [civilian-units.md](../game/civilian-units.md); Merchant and Rail Builder require unlocking tech (Merchant Companies, Early Steam Engine) per [tech-tree-diplomacy-civilian.md](../game/tech-tree-diplomacy-civilian.md) and [tech-tree-transport.md](../game/tech-tree-transport.md). Applied in build phase: deduct cash from treasury and paper from stockpile, add unit at the player's `capitalTile`. **Military:** valid if sufficient stockpile (cost), worker to consume, and regiment unlocking tech; deduct cost, consume worker, add unit **as a member of the Home Army** ([military-armies.md](../game/military-armies.md)). **Naval:** valid if sufficient treasury and stockpile per ship catalog and the player has the **unlocking tech** for that ship type when applicable (see [tech-tree-naval.md](../game/tech-tree-naval.md)); starting ships such as Carrack have no prerequisite. Deduct cost, add ship to home fleet. Unknown unit type is rejected.
- **BuildUnitOrder cost validation (user-visible rejection reasons):** Affordability and prerequisite checks use `canAffordBuild` in `colonizethis_logic` (shared with build application). For **known** failure categories the System returns **distinct** reasons (same vocabulary as work-order treasury/materials messaging): treasury shortfall → `Insufficient treasury`; stockpile shortfall → `Insufficient materials`; required unlocking tech not present in the player’s `techUnlocked` → `Required technology not unlocked`; **military and naval** builds require one available peasant worker — if `WorkerPool.peasants` is zero → `Insufficient workers`. **`Insufficient resources`** is the **generic** fallback for unknown unit type, unknown build category, missing economy catalog row, or any path that does not map to the categories above; `BuildOrderValidator` uses that string only as a last resort if `canAffordBuild` omits a reason.

**Acceptance criteria (BuildUnitOrder rejection messages)**

- Given the player submits a `BuildUnitOrder` for a unit type whose build cost includes treasury and the player’s treasury is below that cost, when the order engine validates the build order, then the system rejects with the reason `Insufficient treasury`.
- Given the player submits a `BuildUnitOrder` for a unit type whose build cost includes stockpile commodities and the stockpile is short of any required commodity, when the order engine validates the build order, then the system rejects with the reason `Insufficient materials`.
- Given the player submits a `BuildUnitOrder` for a unit type that has an unlocking tech requirement and that tech is not `true` in the player’s `techUnlocked`, when the order engine validates the build order, then the system rejects with the reason `Required technology not unlocked`.
- Given the player submits a **military or naval** `BuildUnitOrder` and `WorkerPool.peasants` is zero while treasury and stockpile would otherwise suffice, when the order engine validates the build order, then the system rejects with the reason `Insufficient workers`.
- Given the player submits a `BuildUnitOrder` for an unknown unit type or a type with no resolved build category, when the order engine validates the build order, then the system rejects with the reason `Insufficient resources`.

- **WorkOrder** — Applies to **civilian units only**. Unit id + **target** (action string) + **targetTileKey** (tile key string, format `regionId|provinceId|x|y`). For province-level actions (for example `explore`), `targetTileKey` remains the exact assigned tile key selected/stored for that order; projection/locate and assignment persistence do not rewrite to a synthetic province anchor. **Work ⊆ Move invariant:** for any civilian work order, the unit must also be allowed to occupy `targetTileKey` by the same shared civilian occupancy rules used by `MoveOrder` (`civilianMayOccupyLandTileKey`; see [movement.md](movement.md) § Civilian tile moves). This includes: Explorer `explore`/`prospect` cannot target province-derived foreign Great Power tiles unless tile-level mover control applies; non-Spy civilians cannot enter province-derived foreign Great Power tiles without tile-level mover control. Additional target-specific constraints still apply below (costs, resource/prospection gates, diplomacy gates for the specific target, etc.). Military and naval units do not receive work orders. Supported targets:
  - `explore` — Explorer; province-level; reveals all tiles in province over up to 3 turns (scaled by province size). **Visibility for assignment:** the target province must be **partially revealed** for the ordering player (at least one **land** tile `fogged` or `fullyVisible` and at least one **land** tile `unknown`); see [fog-and-exploration.md](../game/fog-and-exploration.md). See [fog-and-exploration-resolution.md](fog-and-exploration-resolution.md).
  - `prospect` — Explorer; tile-level; prospects the target tile; tile must be mineral-eligible (swamp, hills, mountain, desert). Uses `currentWork` with **one** turn; prospected state updates when work **completes** in Build/Work (not at order accept). See [fog-and-exploration-resolution.md](fog-and-exploration-resolution.md).
  - `build_improvement` — Builder; tile-level; raises improvement level by 1 (subject to terrain and tech caps) after a **multi-turn build**; consumes lumber + cast iron per level. If the tile's resource is a **prospect-required mineral** (same set as [extraction-and-improvements.md](../game/extraction-and-improvements.md) Mineral Prospecting Gate), validation requires that tile to be in the player's prospected set (parity with `purchase_land`).
  - `upgrade_town` — Builder; province town tile; upgrades town to produce materials based on connected resources; multi-turn; costs per ruleset. Requires **`national_bureaucracy`** in `techUnlocked` at validation per [tech-tree-diplomacy-civilian.md](../game/tech-tree-diplomacy-civilian.md).
  - `build_road` — Engineer; tile-level; sets or upgrades transport level (0→1→2) subject to terrain and tech (e.g. Road Construction); multi-turn; consumes lumber + metal.
  - `build_port` — Engineer; coastal town/river tile; creates a port for a (province, seaboard) pair; sets transport level 4 on port tile; multi-turn; consumes lumber + metal.
  - `build_fort` — Engineer; province town tile; increases fort level by 1 (up to max), gated by fort techs (Mine Engineering, Modern Forts) and costs.
  - `build_rail` — Rail Builder; tile-level; upgrades a tile with transport level 1 or 2 to railroad (transport level 4) when per-tile terrain is known and rail tech matches terrain per [tech-tree-transport.md](../game/tech-tree-transport.md); multi-turn; consumes 2 steel + 2 lumber (see `work_order_costs.dart`). Rejects if terrain data is missing, road level is not 1–2, or tech is insufficient for that terrain.
  - `steal_tech` — Spy; target = **other GP's capital province** (targetTileKey identifies that province); up to 5 turns; 8%/turn to steal a random tech the player does not have. Validation: target province is a GP capital; that GP has at least one tech the player lacks.
  - `counter_spy` — Spy; target = any **owned** province; ongoing; each friendly Spy there adds 5%/turn (cap 30%) chance to kill an enemy Spy in that province.
  - `purchase_land` — Merchant; target = tile in **Minor or Tribe** province that has a resource. Validation: tile has resource; if mineral, tile is in player's prospected set; player not at war with that Minor/Tribe; player has **embassy** with that Minor/Tribe; treasury ≥ 15 × resource base price; **tile not already purchased** by any GP (one tile → one buyer; if already purchased by this GP, reject "already own"; if by another GP, reject "already purchased by another power"). Cost: 15 × resource base price (treasury). **Assign-time:** validate affordability only; **do not** debit treasury or record purchase. Uses `currentWork` with **one** turn from `totalTurnsForWork`. **Completion:** debit treasury and update `purchasedTilesByTileKey` when `remainingTurns` reaches 0 in Build/Work (see [development-resolution.md](development-resolution.md)).

- **Civilian deferred primary effects (`prospect`, `purchase_land`):** These targets **must not** apply their primary world effects (prospected set, purchased tile, treasury debit for purchase) at order accept alone. They follow the same **assign → tick → complete** shape as other civilian work: `currentWork` with `totalTurns` from `totalTurnsForWork` (currently `1` for both). Reintroducing an assign-time "instant complete" path for civilians is forbidden; CI enforces rule `no_complete_instant_civilian_order` in `tool/disallowed_ast_patterns.yaml` (see [disallowed-ast-patterns.md](disallowed-ast-patterns.md)).

- **WorkOrder validation:** For every work order type that has treasury or stockpile cost, validate at order submit time: `player.treasury >= cost` (e.g. `purchase_land` affordability at assign; debit still occurs at completion) and/or player stockpile has sufficient materials (build_improvement, build_road, build_port, build_fort, build_rail, upgrade_town). Reject with "Insufficient treasury" or "Insufficient materials" if not met.
- **WorkOrder per-unit uniqueness:** For a given player and turn draft, there is at most **one** pending `WorkOrder` per `unitId`. Validation rejects a second pending work order for the same unit with an explicit reason (e.g. `Only one work order per unit is allowed each turn`).
- **Province-level `targetTileKey` literals (sources + CI):** In app, packages `lib/`, and `tool/` Dart sources (excluding any path under a `test/` directory), a `WorkOrder` literal with `target` in `{explore, steal_tech, counter_spy}` must use a full tile key in `regionId|provinceId|x|y` form (four pipe-delimited segments). CI runs `dart run tool/ct_repo_lint.dart` (rule `repo.canonical_province_tile_keys`; see `SPEC/program/repo-lint.md`) plus the checker’s unit test. Test directories are excluded so fixtures may still include malformed literals for checker coverage.
- **WorkOrder per-tile exclusivity (Builder, Engineer, Merchant):** For a given player and tile (`targetTileKey`), at most one of that player's **Builder**, **Engineer**, or **Merchant** units may have active or newly assigned work targeting that tile in a turn. Validation must:
  - Reject any new Builder/Engineer/Merchant `WorkOrder` whose `targetTileKey` matches the `tileKey` of an existing multi-turn `currentWork` for another Builder/Engineer/Merchant unit owned by the same player.
  - Reject any later Builder/Engineer/Merchant `WorkOrder` in that turn whose `targetTileKey` matches a tile that already appears as `targetTileKey` for an earlier accepted Builder/Engineer/Merchant `WorkOrder` for that player.
  - Use a clear rejection reason (e.g. `Tile already has development or purchase work for this player`) so the app can surface it.
- **Order suggestions and UI availability (colonizethis_logic):** Per-tile reservations for exclusivity (in-progress dev work on the map **plus** pending dev-exclusive `WorkOrder`s for that player) are computed in **`colonizethis_logic`** (e.g. `devExclusiveReservedTileKeysForPlayer` and its use inside `suggestWorkOrders` / `getValidWorkOrderTileKeysWithVisibility`). The Flutter app **must not** duplicate this ruleset; it obtains available work targets and related data **only** via providers that call into that logic (see [order-suggestions.md](order-suggestions.md) § Consumers).

- **WorkOrder resolution:** When a WorkOrder is applied, the **civilian** unit’s **tileKey is set to the order’s targetTileKey**; `currentWork` uses that same tile. On assignment, the system also persists `originTileKey` (pre-assignment tile) and `assignedTileKey` (target tile). On completion, `originTileKey` and `assignedTileKey` are cleared. Multi-turn progress, completion effects, cancellation: [development-resolution.md](development-resolution.md). The same WorkOrder model is used by the main game and by `ctdev`'s `sim_game`. **Cancel in-progress work:** The player may cancel a unit's in-progress work (see [development-resolution.md](development-resolution.md) § Player-initiated cancel). Pending work orders are removed via the order engine's `removeWorkOrder`. In-progress cancel may be implemented as a cancel-work order type (applied at start of Build/Work phase) or as a direct game-state update; TDD specifies.

**Acceptance criteria (work-order per-unit uniqueness)**

- Given a player’s turn draft already contains a pending `WorkOrder` for unit `U`, when the same player submits another `WorkOrder` for `U` in that same turn draft, then the system rejects the second order with an explicit per-unit uniqueness reason and keeps the first order unchanged.
- Given an Explorer owned by player `P` and a `targetTileKey` inside a province-derived Great Power territory owned by another player (with no tile-level purchase/control for `P`), when `P` submits `WorkOrder(target: explore)` or `WorkOrder(target: prospect)` for that tile, then the system rejects the work order because the unit cannot occupy the target tile under civilian occupancy rules.

- **RecruitWorkerOrder** — Player worker pool action. Fields: `targetTier ∈ {peasant, apprentice, journeyman, master}`. Validates affordability and tech gates per [workers-and-population.md](../game/workers-and-population.md) § Recruiting, Training, and Disbanding (authoritative costs and tech gates) and the **peasant reservation ledger** (queued worker actions plus queued military / naval builds; civilian builds do not consume peasants). Rejection reasons mirror that GDD section: `Insufficient workers`, `Insufficient materials`, `Insufficient treasury`, `Required technology not unlocked`. **Applied in Build / work (phase 12) before `BuildUnitOrder`** so worker pool changes settle first (see [turn-resolution-phase-details.md](turn-resolution-phase-details.md) § Build / work). The same order type is emitted for player-facing "Recruit" and "Train" actions (UI may render two controls per tier; both produce `RecruitWorkerOrder` with `targetTier` set). **Disband is not a queued order**; it applies immediately on player action during the Orders phase per the GDD.

- **ResearchOrder** — Per player, per turn: **slot assignments** (slot index → tech id, or empty) and **funding level per slot** (None / Low / Medium / High / Maximum). Valid if: each tech id is in the catalog; all prerequisites of that tech are in the player’s techUnlocked set; slot count ≤ max (3 base, 4 with University); total research cost for the turn ≤ player treasury; tech not already researched. Applied in Research phase: see [research-resolution.md](research-resolution.md), [turn-resolution-phases.md](turn-resolution-phases.md). Merge: human and AI research orders merged like other orders (precedence per order-engine). A tech B that depends on A cannot be in any slot until A is completed.
- **NavalMoveOrder** — Fleet id, **destination** (sea zone id, or port at province id for docking). Valid if: fleet exists and is owned by the player; fleet is **not** the player's home fleet (home fleets cannot move). If fleet is **at sea:** destination must be adjacent (S↔S or P↔S) per topology; if destination is a **port** (docking), the province must be **owned by the player**. If fleet is **in port:** destination must be an adjacent sea zone (undock). Applied in Movement phase: fleet location updated; ship reveal triggered when fleet enters a sea zone. See [naval-movement-resolution.md](naval-movement-resolution.md), [ships-and-naval.md](../game/ships-and-naval.md).
- **NavalMissionOrder** — Fleet id, **mission** (e.g. patrol, blockade, beachhead, join_home_fleet). Valid if: fleet exists and is owned by the player; mission is valid per [ships-and-naval.md](../game/ships-and-naval.md) § Missions and Movement. **Join home fleet** is valid only when the fleet is **in port at the player's capital province**. Home fleets may only receive the special `join_home_fleet` mission when used as the **target** of a join operation; they cannot be assigned Patrol/Blockade/Beachhead/Defend. Patrol/Blockade/Beachhead/Defend apply only to fleets **at sea**. Applied in Movement phase (mission assignment and join-home-fleet resolution); interception and combat in Naval Interception & Naval Combat step per [turn-resolution-phases.md](turn-resolution-phases.md). See [naval-movement-resolution.md](naval-movement-resolution.md), [naval-combat-resolution.md](naval-combat-resolution.md), [ships-and-naval.md](../game/ships-and-naval.md).
- **TradeOrder** — `commodityId`, **`type`** (`bid` / `offer`), `quantity` (non-negative int), `priority` (positive int; 1 = highest), `isFtp` (derived during matching). Stored on `Orders.tradeOrdersByPlayerId` (`Map<String, List<TradeOrder>>`); the resolved market state lives on `Game.worldMarketState`. Resolved in **Phase 13 World Market** (between Build / work and End-of-turn). Submission-time validation (per-commodity cap, mutual exclusion, bid-type cap `0 / 3 / 6` via `worldMarketBidTypeCap`, stockpile / cargo sufficiency, riches exclusion) is performed by `TradeOrderValidator` per [world-market-resolution.md § Trade order validation](world-market-resolution.md). Validated in [OrderEngine](order-engine.md) via `addTradeOrder` / `addTradeOrderWithContext` after naval orders in the per-player validation pass.

- **DiplomaticOrder** — **type** (declareWar, offerPeace, alliance, establishOverture, grantAid, setSubsidy), **targetFactionId**, optional **amount** (grantAid, setSubsidy), optional **overtureStage** (establishOverture). Establish Overture **target** may be Minor Nation, Tribe, or Great Power. Toward Minor/Tribe, Trade Consulate / Embassy / NAP stages require **`diplomatic_expertise`** in the submitter’s `techUnlocked`. **Join Empire** (`overtureStage` join empire) toward a **Great Power** requires **`empire_building`** and a **nearly defeated** target per [diplomacy.md](../game/diplomacy.md). Valid if preconditions per [diplomacy.md](../game/diplomacy.md) § Diplomatic Order Types (AT_PEACE/AT_WAR, overture stage, treasury, tech) are met; checked at submission and at resolution. **At most one diplomatic order per (submitting player, targetFactionId, order type)** for types `declareWar`, `offerPeace`, `alliance`, and `establishOverture` — at most one of these four toward the same T in one list. **Exception:** `grantAid` and `setSubsidy` may **both** appear toward the same T in the same list (one grant and one subsidy), and each of those types may appear at most once each toward T. A non-economic order toward T **blocks** any further order toward T in that list (including `grantAid` and `setSubsidy`). Other pairwise combinations toward the same T remain rejected (e.g. cannot submit both `declareWar` and `alliance` toward T). **Amount granularity:** `grantAid` `amount` must be a **positive multiple of £1000**; `setSubsidy` `amount` must be a **positive multiple of £100** (aligned with UI steppers in [diplomacy-panel.md](../ui/diplomacy-panel.md)). Constants in `colonizethis_logic`: `grantAidDefaultAmount`, `setSubsidyDefaultAmount`, `grantAidAmountStep`, `setSubsidyAmountStep`. **Submission:** reject with a reason referencing the required step when amounts violate multiples. **Resolution:** if an order reaches resolution with an amount that violates those multiples, the system treats that as a **hard error** (fails loudly; not a silent skip). Applied in Diplomacy phase (before Movement): target accepts or rejects at resolution; see [diplomacy-resolution.md](diplomacy-resolution.md), [turn-resolution-phases.md](turn-resolution-phases.md).

**Acceptance criteria (diplomatic order cap)**

- Given a Great Power player P and a valid target faction T, when P’s submitted diplomatic order list for the turn already contains a `DiplomaticOrder` of type `declareWar`, `offerPeace`, `alliance`, or `establishOverture` toward T, then the system rejects any **additional** diplomatic order toward T whose type is any of those four, with a reason that P already has a diplomatic order for that faction this turn.
- Given P’s list toward T already contains a non-economic `DiplomaticOrder`, when P appends any further `DiplomaticOrder` toward T (including grantAid or setSubsidy), then the system rejects it with a reason that P already has a diplomatic order for that faction this turn (or an equivalent explicit rejection).
- Given P’s list already contains `grantAid` toward T, when P appends a second `grantAid` toward T in the same list, then the system rejects the duplicate with a clear reason.
- Given P’s list already contains `setSubsidy` toward T, when P appends a second `setSubsidy` toward T in the same list, then the system rejects the duplicate with a clear reason.
- Given P’s list contains `grantAid` toward T and no `setSubsidy` toward T, when P appends a valid `setSubsidy` toward T, then the system accepts it under normal type-specific rules.
- Given P’s list contains no diplomatic order toward T, when P appends a single valid `DiplomaticOrder` toward T, then the system accepts that order under the normal type-specific rules.
- Given P submits `grantAid` with `amount` not divisible by 1000, or `setSubsidy` with `amount` not divisible by 100, then the system rejects that order with a reason that references the required step.

**Diplomatic sub-validators (implementation):** Type-specific diplomatic rules live in per-type sub-validators under `colonizethis_logic` `lib/src/orders/validators/diplomatic/`. Each implements the `DiplomaticSubValidator` interface: `validate(order, treasury)` returns an `OrderValidationResult` and the post-validation treasury (unchanged on reject; debited on accept for economic types). The parent `DiplomaticOrderValidator` runs cross-cutting checks (target existence, self-target, per-target cap) before dispatch. Shared helpers in `diplomatic_sub_validator.dart` supply `DiplomaticSubValidatorContext`, `relationDiplomaticSubValidator` (relation fetch + check), and `delegatedDiplomaticSubValidator` (custom check). All per-type modules are factory functions backed by these helpers; multi-stage overture logic uses private per-stage helpers inside the `establishOvertureSubValidator` factory (no bespoke `implements DiplomaticSubValidator` class). The repo-lint rule `repo.logic_diplomatic_sub_validator_size` (Refs #2560) enforces this contract: any `class X implements DiplomaticSubValidator` declared in `lib/src/orders/validators/diplomatic/` outside the shared contract file `diplomatic_sub_validator.dart` is a CI violation; the sanctioned `_DelegatedDiplomaticSubValidator` adapter inside the contract file is also bounded to 30 non-empty body lines so the adapter cannot drift into bespoke type-specific logic.

## Validation and Resolution

Validation rules (topology, costs, caps, visibility) and resolution phase ordering: see [order-engine.md](order-engine.md). Rejected orders are not applied; state unchanged.
