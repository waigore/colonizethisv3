## Phase planner dispatcher (Refs #2509 S5 foundation)

**SPEC/ai** sub-spec for the `runPhasePlanners` dispatcher and `PhasePlanOutcome` value class. Companion to [phase-planner-architecture.md](phase-planner-architecture.md) § Orchestrator dispatch; derives from [ai-architecture.md](ai-architecture.md) § Observer goal phases.

## Overview

`phase_planner_dispatch.dart` (in `packages/colonizethis_ai/lib/src/planning/`) exposes a single pure function `runPhasePlanners({game, snapshot, personalityId})` that calls `observerGoalPhaseFor(snapshot, game)` once and composes the per-phase planner outputs into a `PhasePlanOutcome` value class.

The dispatcher is the wiring layer between phase resolution and the per-domain pure-function planner modules. It performs no I/O, no logging, no order emission, and is deterministic by construction (Must-have #7). The orchestrator (S5) consumes `PhasePlanOutcome` to feed `runDiplomacyPlannerWithResult`, the economy passes, and the army-move planner without re-checking phase in every call site.

**Orchestrator diplomacy slices (landed):** `domain_planner_orchestrator.dart` calls `runPhasePlanners` once per player turn and threads the result into every `runDiplomacyPlannerWithResult` invocation. `_stalledPeacePlannerResultIfNeeded` uses `gpPeaceTargetsFromPhasePlan` instead of `collectStalledGreatPowerPeaceTargets` when `phasePlan` is set. `_phasePlannerDeclareWarPlannerResultIfNeeded` forces `declareWar` from `gpExpandDeclareWarTargetFromPhasePlan` / `gpColonialDeclareWarTargetFromPhasePlan`; when both return `null` the EXPAND ratchet aggregator (`expandRatchetGreatPowerPeaceTargets`, canonical home `observer_goal_phase.dart`) runs as fallback to preserve dev-pinned below-quota minor and GP-only invadable frontier blocker contracts during the S5 migration. The legacy `colonial_pressure.dart` and `diplomacy_planner_peace_targets.dart` files were deleted in S1; their helpers are canonical in the phase-planner modules and `observer_goal_phase.dart`.

**Orchestrator conquest slice (landed):** `runConquestArmyMovePlanner` accepts optional `phasePlan` from the orchestrator. `resolvePhaseConquestInvadable` (`phase_planner_conquest_filter.dart`) restricts the invadable destination set to `expandMilitaryPlanFromPhasePlan` / `colonialMilitaryPlanFromPhasePlan` when either plan is non-default; when both are default it falls back to the legacy invadable union with structural NW suppression under EXPAND / COLONIAL-lite and skips the pass entirely under DEVELOP. When `phasePlan` is set, `resolvePhaseConquestColonialPressureActive` drives the colonial-pressure minimum weight floor (`kConquestArmyMoveMinWeightWhenColonialPressure`) — active only under COLONIAL — and `resolvePhaseConquestSuppressNwInvasionScoring` drives NW invadable army-move destination scoring suppression (EXPAND, COLONIAL-lite, DEVELOP suppress; COLONIAL allows), replacing the legacy `hasColonialAcquisitionTargets` / `shouldSuppressNewWorldDeclareWarInvasionAndPurchase` predicates at those call sites. `null` `phasePlan` preserves the legacy predicates exactly. Economy wiring remains on the legacy path until a later S5 slice.

**Orchestrator naval slice (landed):** `runNavalPlanner` accepts optional `phasePlan` from the orchestrator. `resolvePhaseNavalDirective` (`phase_planner_naval_filter.dart`) drives the colonial-pressure naval boost + ranking from the active phase: COLONIAL and COLONIAL-lite engage the boost (structural — already gated on `hasColonialAcquisitionTargets` / `globalNewWorldHasNonGpOwnership` at phase entry), while EXPAND and DEVELOP structurally suppress it. When `phasePlan` is `null` the planner keeps the legacy `hasColonialAcquisitionTargets` + `shouldSuppressNewWorldColonialOrders` gate so prior tests stay green; the orchestrator always passes the dispatched plan. The resolver also surfaces the per-phase priority NW province list (`ColonialNavalPlan.priorityInvasionTransportProvinceIdsSorted` under COLONIAL; `ColonialLiteNavalPlan.priorityNwProvinceIdsSorted` under COLONIAL-lite); `runNavalPlanner` threads that list into both `sortNavalMovesForColonialPressure` and `sortNavalMissionsForColonialPressure`. Naval-move ranking promotes NW sea zones adjacent to phase-priority provinces to `kColonialNavalMovePhasePriorityNwSeaZoneScore` (240) — one tier above `kColonialNavalMovePriorityNwSeaZoneScore` (200). Naval-mission ranking promotes missions whose `targetPortId` (or `targetProvinceId`) lies in the phase-priority subset to `kColonialNavalMissionPhasePriorityNwPortScore` (200) / `kColonialNavalMissionPhasePriorityNwProvinceScore` (170) — one tier each above `kColonialNavalMissionNwPortScore` (160) / `kColonialNavalMissionNwProvinceScore` (130). Non-priority NW destinations keep the existing general tiers; OW gateway / generic NW / dock / beachhead / OW branches are unaffected. Empty / null priority list (legacy callers, `defaultPlan` arms) preserves the prior scoring exactly.

**Orchestrator economy work-suggestion slice (landed):** `_runEconomyDomainPlanners` consumes the same `PhasePlanOutcome` and drops disallowed civilian suggestions via `shouldSuppressWorkOrderFromPhasePlan` (`phase_planner_work_order_filter.dart`); dispatch is pure on `outcome.phase`. This replaces the per-candidate `shouldFilterObserverPhaseWorkOrder` call (`observer_goal_phase.dart`) which re-invoked `observerGoalPhaseFor` for every suggestion. The legacy per-candidate helper remains exported by `observer_goal_phase.dart` for tests that have not yet migrated to the dispatched path.

**Orchestrator economy colonial-pressure slice (landed):** `_runEconomyDomainPlanners` derives the colonial economy boost from the dispatched `PhasePlanOutcome` via `resolvePhaseEconomyColonialPressureActive` (`phase_planner_economy_filter.dart`) instead of the legacy `hasColonialAcquisitionTargets && !isStalledOldWorldGpBlockerFocus && !shouldSuppressNewWorldColonialOrders` three-predicate compute. The boost (lower civilian work threshold to `kColonialCivilianWorkThresholdCap`, force `runFullAiCivilianWork`, set `BuildPickInput.colonialPressure: true` for the cargo-ship bonus) is active only under COLONIAL — structurally suppressed under EXPAND, COLONIAL-lite, and DEVELOP, mirroring `resolvePhaseConquestColonialPressureActive`. COLONIAL-lite is intentionally excluded so the OW quota push is not weakened by NW economic bias under the safeguard (issue #2509 § COLONIAL-lite "Begin NW penetration without weakening OW push"); the COLONIAL-lite naval/overture safeguard runs independently of the economy boost. The tagalong `snapshot.colonial.newWorldProvincesOwned > 0` guards at the orchestrator call sites still independently lower the civilian threshold and gate `runFullAiCivilianWork`, so GPs that already own NW provinces continue receiving the civilian-planner pass under EXPAND / COLONIAL-lite — only the *acquisition-pressure* boost is gated by the resolver.

**Orchestrator economy DEVELOP-gate slice (landed):** `_runEconomyDomainPlanners` derives the DEVELOP economy gate from the dispatched `PhasePlanOutcome` via `resolvePhaseEconomyDevelopActive` (`phase_planner_economy_filter.dart`) instead of recomputing `isObserverDevelopPhase(snapshot, game)` per player turn. The resolver is pure on `outcome.phase` and returns `true` only under DEVELOP — structurally suppressed under EXPAND, COLONIAL-lite, and COLONIAL, mirroring the partition matrix established by the declare-war suppression resolvers (`resolvePhaseDiplomacyDeclareWar*SuppressionActive`). The gate drives two economy-pass decisions: (a) lowering the civilian work threshold to `kDevelopCivilianWorkThresholdCap` so DEVELOP improvement planning triggers below the default weight bar, and (b) forcing `runFullAiCivilianWork` so the planner runs even when domain weights would otherwise gate it out. The phase dispatcher already resolved `observerGoalPhaseFor` once via `runPhasePlanners`, so phase-derived `true/false` is field-equal to the legacy `isObserverDevelopPhase` compute across every `ObserverGoalPhase` value, preserving the prior DEVELOP economy behaviour exactly during the S5 migration. The two economy resolvers (`resolvePhaseEconomyColonialPressureActive` and `resolvePhaseEconomyDevelopActive`) form a *disjoint* matrix — at most one returns `true` for any given `outcome.phase`, never both, so the orchestrator cannot simultaneously treat the active player as in COLONIAL acquisition pressure and DEVELOP improvement push.

**Orchestrator declare-war scoring colonial-pressure slice (landed):** `runDiplomacyPlannerWithResult` threads the dispatched `PhasePlanOutcome` into `computeDiplomaticCandidateScores`; `_DeclareWarTargetContext.build` (`diplomatic_candidate_scoring_declare_war.dart`) derives the candidate's `colonialPressure` slot from `resolvePhaseDiplomacyDeclareWarColonialPressureActive` (`phase_planner_diplomacy_filter.dart`) instead of the legacy `hasColonialAcquisitionTargets && !isStalledOldWorldGpBlockerFocus && !shouldSuppressNewWorldColonialOrders` three-predicate compute. The slot drives the `colonialPressure && ownsInvadableNw` exception in `_declareWarSuppressedWarConcentrationScore` that keeps a tribe-target declare-war candidate scorable when the tribe owns an invadable NW province under stalled-OW + behind-victory-pace preconditions; phase-derived `colonialPressure` is active only under COLONIAL — structurally suppressed under EXPAND, COLONIAL-lite, and DEVELOP, mirroring `resolvePhaseConquestColonialPressureActive` and `resolvePhaseEconomyColonialPressureActive`. COLONIAL-lite is structurally excluded because issue #2509 § COLONIAL-lite scope summary forbids NW `declareWar` outright; `_declareWarSuppressedColonialLiteScore` already collapses NW colonial targets in COLONIAL-lite before the war-concentration scoring branch runs, so the resolver returning `false` makes that suppression contract explicit at the colonial-pressure layer. EXPAND collapses NW colonial targets via `_declareWarSuppressedExpandColonialScore`, and DEVELOP collapses every declare-war candidate via `_declareWarSuppressedDevelopPhaseScore`, so the structural `false` resolution under those phases preserves the prior scoring outcomes exactly. When `phasePlan` is `null` (legacy callers and tests that pre-date the threading), `_DeclareWarTargetContext.build` keeps the legacy three-predicate compute so existing scoring behavior is preserved during the S5 migration. The legacy three-predicate compute remains available for the `null`-phase compatibility path until every consumer migrates.

**Orchestrator conquest extra-passes slice (landed):** `runDomainPlannersWithOutcome` derives the extra-conquest-passes / relocation-skip gate from the dispatched `PhasePlanOutcome` via `resolvePhaseConquestExtraPassesActive` (`phase_planner_conquest_filter.dart`) instead of recomputing the legacy compound `isStalledOldWorldExpansion(ow) || isBelowObserverConquestQuota(ow)` (`colonizethis_data`). The two predicates are equivalent for integer `ow` (both reduce to `ow <= 9`) and field-equal to `phase ∈ {EXPAND, COLONIAL-lite}` because both phases require `oldWorldProvincesOwned < kObserverConquestMinOwProvincesPerGp` (10) at entry via `observerGoalPhaseFor`. The resolver is pure on `outcome.phase` and gates two orchestrator decisions: (a) the orchestrator runs `kStalledConquestArmyMovePasses` passes through `runConquestArmyMovePlanner` instead of one so a below-quota GP gets multiple chances to commit invadable-frontier moves in the same turn, and (b) the orchestrator skips the follow-up `runArmyMovePlanner` (relocation) pass so frontier marches committed by the conquest passes are not undone by an opportunistic relocation back toward the capital. The relocation skip is the *negation* of this resolver: under COLONIAL / DEVELOP (above quota) the relocation pass runs normally and only one conquest pass fires. The two conquest-routing resolvers (`resolvePhaseConquestExtraPassesActive` and `resolvePhaseConquestColonialPressureActive`) form a *partition* matrix over the non-DEVELOP phases — EXPAND and COLONIAL-lite engage extra passes only (no NW minimum weight floor); COLONIAL engages the NW floor only (no extra passes); DEVELOP engages neither (the conquest pass itself is skipped via `resolvePhaseConquestInvadable.skipConquestPass`). The complete elimination of `isStalledOldWorldExpansion` / `isBelowObserverConquestQuota` calls in `runDomainPlannersWithOutcome` removes two per-player-turn predicate recomputes.

**Orchestrator economy build-pass slice (landed):** `_appendEconomyBuildOrders` derives below-quota OW build routing from the dispatched `PhasePlanOutcome` via `resolvePhaseEconomyExpandQuotaPressureActive` (`phase_planner_economy_filter.dart`; field-equal to `resolvePhaseConquestExtraPassesActive`) instead of recomputing `isStalledOldWorldExpansion(ow)` / `isBelowObserverConquestQuota(ow)` per build pass. The resolver gates: (a) the stalled build-threshold cap (`min(buildThreshold, 15)`), (b) `observerQuotaPressure` and the `isBelowQuotaPeace*` regiment-rebuild helpers, and (c) the `forceRegimentRebuild` stalled-expansion arm. The GP-blocker-focus cap (`min(buildThreshold, 8)`) and the `primaryInvadableOldWorldGpBlocker` lookup for `atWarWithGpBlocker` / `minRegimentFloor` now route through `resolvePhaseEconomyExpandGpBlockerFocusActive` and `expandPrimaryInvadableGpBlockerFromPhasePlan`, which read `expandGpOnlyInvadableFrontierActive` and `expandPrimaryInvadableGpBlockerFactionId` populated once in `runPhasePlanners` via `expandIsOldWorldGpOnlyInvadableFrontier` / `expandPrimaryInvadableOldWorldGpBlocker` — field-equal to legacy `isStalledOldWorldGpBlockerFocus` / `primaryInvadableOldWorldGpBlocker` when `resolvePhaseEconomyExpandQuotaPressureActive` is already `true`. The COLONIAL build threshold cap (`colonialBuildOrderThresholdCap`) applies only when `resolvePhaseEconomyColonialPressureActive` is `true` (COLONIAL phase) — structurally suppressed under EXPAND, COLONIAL-lite, and DEVELOP so NW-owned GPs in EXPAND no longer receive the colonial build cap outside COLONIAL. The EXPAND regiment-rebuild directive (`ExpandEconomyPlan.forceCheapestRegimentBuild`) is read from `expandEconomyPlanFromPhasePlan` (already computed once in `runPhasePlanners`) and composes with the legacy GP-blocker / critically-weak arms: when `forceCheapestRegimentBuild` is `true`, the build pass drops `buildThreshold` to zero and sets `BuildPickInput.militaryRebuildCrisis` even when the legacy `forceRegimentRebuild` compound would not have fired alone.

**Orchestrator economy build rebuild-trap slice (landed):** `_appendEconomyBuildOrders` derives the two `isBelowQuotaPeace*` rebuild-trap signals from the dispatched `PhasePlanOutcome` via `resolvePhaseEconomyExpandBelowQuotaPeaceInsufficientRegimentsActive` and `resolvePhaseEconomyExpandBelowQuotaPeaceZeroRegimentsRebuildActive` (`phase_planner_economy_filter.dart`) instead of calling `isBelowQuotaPeaceInsufficientRegiments` and `isBelowQuotaPeaceZeroRegimentsRebuild` (canonical home `expand_phase_planner.dart` since the S1 deletion of `colonial_pressure.dart`). The two new resolvers fold the prior `expandQuotaPressure &&` orchestrator prefix into the phase gate — `resolvePhaseEconomyExpandQuotaPressureActive` is itself field-equal to `isBelowObserverConquestQuota(ow)` because EXPAND and COLONIAL-lite phase entry both require `oldWorldProvincesOwned < kObserverConquestMinOwProvincesPerGp` via `observerGoalPhaseFor`, so the legacy helpers' first guard (`isBelowObserverConquestQuota(ow)`) is satisfied structurally; the remaining `!atWarWithAnyGreatPower && 0 < regimentCount < kBelowQuotaPeaceMinRegimentsBeforeDeclareWar && hasInvadableProvinces` (insufficient-regiments arm) and `regimentCount == 0 && hasInvadableProvinces` (zero-regiments arm) arms are evaluated directly inside the new resolvers. The two `_appendEconomyBuildOrders` consumers (`belowQuotaPeaceInsufficientRegiments` and `belowQuotaZeroRegimentsRebuild`) — both of which feed `forceRegimentRebuild`, `militaryRebuildCrisis`, and (for the zero-regiment arm) the `minRegimentFloor = 1` directive — now route through the phase-derived resolvers and the orchestrator drops its `import 'colonial_pressure.dart'` line entirely. Phase-derived `bool` is field-equal to the legacy compose under EXPAND across every reachable `(ow ∈ [0, kObserverConquestMinOwProvincesPerGp), regimentCount, atWarWithAnyGreatPower, hasInvadableProvinces)` combination — the unit-test parity matrix in `phase_planner_economy_filter_test.dart` pins this invariant. COLONIAL-lite routes identically to EXPAND so the OW push is not weakened by NW overture / naval activity (issue #2509 § COLONIAL-lite "Begin NW penetration without weakening OW push"); COLONIAL and DEVELOP collapse to `false` structurally because the rebuild trap does not apply at or above quota. With `colonial_pressure.dart` deleted in S1, `domain_planner_orchestrator.dart` carries no live import to the legacy file; remaining mentions appear only as historical context in narrative SPEC slices and code dartdoc.

**Orchestrator economy build colonial-cap slice (landed):** `_appendEconomyBuildOrders` derives the COLONIAL build-order threshold cap from the dispatched `PhasePlanOutcome` via `resolvePhaseEconomyColonialBuildOrderThresholdCap` (`phase_planner_economy_filter.dart`) instead of calling the legacy `colonialBuildOrderThresholdCap(snapshot.colonial)` (formerly in `colonial_pressure.dart`, since deleted). The legacy helper had two arms keyed on `hasColonialAcquisitionTargets(colonial)` — under-pressure (`kColonialBuildOrderThresholdWhenOwnedNwUnderPressure`, 15) when both `hasColonialAcquisitionTargets` and `newWorldProvincesOwned > 0` held, and a fallback constant (value 18, since retired) when only `newWorldProvincesOwned > 0` held without acquisition targets. The orchestrator only invoked the helper inside the outer `if (colonialPressure)` guard, where `colonialPressure` is `resolvePhaseEconomyColonialPressureActive` (active only under COLONIAL). COLONIAL phase entry is itself gated on `hasColonialAcquisitionTargets` via `observerGoalPhaseFor`, so the first legacy arm was the *only* reachable arm at the orchestrator's call site — the no-acquisition fallback required `!hasColonialAcquisitionTargets`, which is structurally unreachable inside the orchestrator's COLONIAL-pressure branch. The resolver therefore collapses the helper's reachable behaviour to a single phase-derived path: returns `kColonialBuildOrderThresholdWhenOwnedNwUnderPressure` when phase is COLONIAL and `colonial.newWorldProvincesOwned > 0`; returns `null` otherwise. Phase-derived `int?` is field-equal to the legacy compute at the orchestrator's only call site across every reachable `(ObserverGoalPhase, ColonialSummary)` pair, preserving the prior build-threshold cap behaviour exactly during the S5 migration. Structural suppression mirrors `resolvePhaseEconomyColonialPressureActive`: EXPAND / COLONIAL-lite / DEVELOP all return `null` regardless of `newWorldProvincesOwned` (NW-owned GPs in EXPAND no longer receive the colonial cap outside COLONIAL, matching the existing colonial-pressure slice). The legacy `colonialBuildOrderThresholdCap` function was retired along with the deletion of `colonial_pressure.dart` (Refs #2509 S1) — the legacy helper had no remaining callers outside its own test fixtures, and the structurally-unreachable second arm made it ineligible for a thin delegating stub. The retired no-acquisition fallback constant (value 18) has now also been removed from `colonizethis_data` (Refs #2509) — the symmetry it provided with the under-pressure constant served no production path, and the regression-guard test at `phase_planner_economy_filter_test.dart` § "returns the under-pressure constant, never the retired no-acquisition fallback value (18)" now pins the literal `isNot(18)` invariant directly so a future regression that wired the wrong numeric cap still flips the pin.

**Strategic goal-scoring slice (landed):** `generateStrategicOrders` (`strategic_ai.dart`) resolves `observerGoalPhaseFor(snapshot, game)` once per player turn and threads the resulting `ObserverGoalPhase` into `evaluateStrategicGoalScores` / `selectPrimaryGoal` instead of recomputing `isStalledOldWorldGpBlockerFocus || isBelowObserverConquestQuota` and the legacy three-predicate colonial-pressure block (`hasColonialAcquisitionTargets && !stalledFocus && !shouldSuppressNewWorldColonialOrders`). `resolvePhaseGoalSuppressColonialPressure` (`phase_planner_goal_filter.dart`) is active under EXPAND and COLONIAL-lite — field-equal to the legacy suppress compound because below-quota phases already satisfy `isBelowObserverConquestQuota` and the GP-blocker arm is a subset. `resolvePhaseGoalColonialPressureActive` is active only under COLONIAL — field-equal to the legacy colonial-pressure score floors on the production path, mirroring `resolvePhaseEconomyColonialPressureActive`. Legacy callers that omit `observerGoalPhase` keep the prior `suppressColonialPressure` bool and snapshot-derived predicates for unit tests.

**Strategic-AI hoisted phase-plan slice (landed):** `generateStrategicOrdersWithTrace` (`strategic_ai.dart`) calls `runPhasePlanners(game: planningGame, snapshot: planningSnapshot, personalityId: config.personalityId)` once after `prepareConquestFieldArmy` resolves the planning-state pair, and threads the resulting `PhasePlanOutcome` into `runDomainPlannersWithOutcome` via a new optional `phasePlan` parameter. `runDomainPlannersWithOutcome` (and the convenience `runDomainPlanners` entry) now accept `PhasePlanOutcome? phasePlan` and short-circuit the internal `runPhasePlanners` compute (`phasePlan ?? runPhasePlanners(...)`) when the caller already supplied a plan; legacy callers that omit the parameter still trigger the internal dispatch so existing orchestrator-level test fixtures stay green during the S5 migration. The hoist collapses the prior per-AI-turn double-dispatch (one in the strategic-AI layer, one inside the orchestrator) to a single call against the same `(planningGame, planningSnapshot, personalityId)` inputs and prepares the next S5 slice to route the same `PhasePlanOutcome` into `runEconomyPlanner` so the last in-tree planner resolving phase signals via legacy helpers (now canonical in `expand_phase_planner.dart` since the S1 deletion of `colonial_pressure.dart`) can migrate without recomputing the dispatch a third time.

**Economy planner hoisted phase-plan slice (landed):** `generateStrategicOrdersWithTrace` (`strategic_ai.dart`) now dispatches `runPhasePlanners(planningGame, planningSnapshot, config.personalityId)` *before* calling `runEconomyPlanner` and threads the resulting `PhasePlanOutcome` into the planner via a new optional `phasePlan` named parameter. `runEconomyPlanner` (`economy_planner.dart`) derives the EXPAND below-quota peace treasury-recovery cargo boost from the dispatched phase via `resolvePhaseEconomyExpandBelowQuotaPeaceZeroRegimentsRebuildActive` and `resolvePhaseEconomyExpandBelowQuotaPeaceInsufficientRegimentsActive` (`phase_planner_economy_filter.dart`) when `phasePlan` is supplied, instead of calling `isBelowQuotaPeaceTreasuryRecovery` (canonical home `expand_phase_planner.dart` since the S1 deletion of `colonial_pressure.dart`). The treasury affordability arm (`treasury + pendingRichesTreasuryDelta(...) < cheapestRegimentBuildTreasuryCost()`) is preserved unchanged — the migration only swaps the phase-signal path. Phase-derived `bool` is field-equal to the legacy compute under EXPAND / COLONIAL-lite because both phases require `oldWorldProvincesOwned < kObserverConquestMinOwProvincesPerGp` at entry via `observerGoalPhaseFor`, satisfying the legacy `isBelowObserverConquestQuota` guard structurally; under COLONIAL and DEVELOP the resolvers collapse to `false` mirroring the orchestrator's economy build-pass slice. Legacy callers that omit the parameter (including `economy_planner_test.dart` snapshot-only fixtures) still trigger the legacy compute so existing tests stay green during the S5 migration. With the economy planner migrated, every in-tree strategic-AI consumer of phase signals now reads the hoisted dispatch directly. The legacy `colonial_pressure.dart` file has since been deleted in S1; the non-phase helpers it previously hosted (`pendingRichesTreasuryDelta` boundary checks, the regiment-cost catalog scan) have moved to their canonical homes in the planning modules.

**Orchestrator declare-war scoring phase-suppression slice (landed):** `_DeclareWarTargetContext` carries the dispatched `PhasePlanOutcome` as a field so the three sibling phase-suppression scoring branches read the active phase off a single dispatched value rather than recomputing `observerGoalPhaseFor` per declare-war candidate. `_declareWarSuppressedDevelopPhaseScore` derives DEVELOP suppression from `resolvePhaseDiplomacyDeclareWarDevelopSuppressionActive` (`phase_planner_diplomacy_filter.dart`) instead of `isObserverDevelopPhase`. `_declareWarSuppressedColonialLiteScore` derives COLONIAL-lite NW-collapse suppression from `resolvePhaseDiplomacyDeclareWarColonialLiteSuppressionActive` instead of `observerGoalPhaseFor(...) == colonialLite`. `_declareWarSuppressedExpandColonialScore` derives EXPAND NW-collapse suppression from `resolvePhaseDiplomacyDeclareWarExpandColonialSuppressionActive` instead of `shouldSuppressNewWorldColonialOrders`. The three resolvers are pure on `outcome.phase` and field-equal to their legacy per-candidate computes across every `ObserverGoalPhase` value, so the migration is behaviour-preserving for the three suppression branches. The phase-suppression resolvers form a *partition* matrix — exactly one of the three returns `true` for any given `outcome.phase`, and all three return `false` under COLONIAL (where every declare-war candidate scores normally; the `colonialPressure && ownsInvadableNw` exception in `_declareWarSuppressedWarConcentrationScore` handles tribe-target preservation under COLONIAL). When `phasePlan` is `null` (legacy callers and tests that pre-date the threading), the three branches keep their legacy `observerGoalPhaseFor`-recomputing path so existing scoring tests stay green. The legacy per-candidate `observerGoalPhaseFor` recompute remains available for the `null`-phase compatibility path until every consumer migrates.

## Rules

### Dispatch matrix

| Phase | Calls (in order) |
|-------|------------------|
| `expand` | `planExpandDeclareWar`, `planExpandPeace`, `planExpandEconomy`, `planExpandMilitary(declaredWarTargetFactionId)` |
| `colonialLite` | All four EXPAND calls, plus `planColonialLiteOvertures`, `planColonialLiteNaval` |
| `colonial` | `planColonialAcquisition(personalityId)`, `planColonialPeace`, `planColonialMilitary(colonialDeclaredWarTargetFactionId)`, `planColonialNaval(colonialDeclaredWarTargetFactionId)`, `planColonialCivilian` |
| `develop` | `planDevelopPeace`, `planDevelopCivilian` |

### Argument pairing

- The EXPAND `declareWarTargetFactionId` argument to `planExpandMilitary` is the same value `planExpandDeclareWar` returned in this dispatch call (may be `null`).
- The COLONIAL `colonialDeclaredWarTargetFactionId` argument to both `planColonialMilitary` and `planColonialNaval` is `colonialAcquisitionTarget.targetFactionId` only when the resolved acquisition method is `AcquisitionMethod.declareWar`. For `joinEmpire`, `purchase_land`, or `null` acquisitions the argument is `null`, so the military/naval pair falls back to the at-war arm.
- The `personalityId` argument is forwarded to `planColonialAcquisition`; it is dead for non-COLONIAL phases.

### Suppression matrix (PhasePlanOutcome slots)

`PhasePlanOutcome` carries one slot per planner output. Slots unused by the active phase carry default-plan or empty values so callers may read every slot unconditionally.

| Phase | Slots populated with non-default content |
|-------|------------------------------------------|
| `expand` | `expandDeclareWarTargetFactionId`, `expandPeaceTargetFactionIdsSorted`, `expandEconomyPlan`, `expandMilitaryPlan`, `expandGpOnlyInvadableFrontierActive`, `expandPrimaryInvadableGpBlockerFactionId` |
| `colonialLite` | All EXPAND slots above, plus `colonialLiteOverturesSorted`, `colonialLiteNavalPlan` |
| `colonial` | `colonialAcquisitionTarget`, `colonialPeaceTargetFactionIdsSorted`, `colonialMilitaryPlan`, `colonialNavalPlan`, `colonialCivilianWorkOrders` |
| `develop` | `developPeaceTargetFactionIdsSorted`, `developCivilianWorkOrders` |

Full-COLONIAL slots stay default under COLONIAL-lite. This is the structural NW-acquisition suppression for the colonial-lite safeguard — the dispatcher never calls `planColonialAcquisition`, `planColonialMilitary`, `planColonialNaval`, or `planColonialCivilian` in `colonialLite`, so `declareWar` / `joinEmpire` / `purchase_land` / invasion-transport are unreachable per spec.

### Default outcome constants

`PhasePlanOutcome.defaultExpand`, `.defaultColonialLite`, `.defaultColonial`, `.defaultDevelop` provide const-shared all-default instances per phase for short-circuit returns when every planner in the set reaches its outer guard.

### Adapter helpers

Pure adapter functions extract per-domain orchestrator-ready values from a single `PhasePlanOutcome`. The orchestrator calls `runPhasePlanners` once per player turn and consumes the adapters' outputs repeatedly without re-checking the active phase. All adapters are pure and deterministic (Must-have #7).

| Adapter | Module | Output | EXPAND | COLONIAL-lite | COLONIAL | DEVELOP |
|---|---|---|---|---|---|---|
| `gpPeaceTargetsFromPhasePlan` | `phase_planner_peace_targets.dart` | `List<String>` GP `offerPeace` targets | `expandPeaceTargetFactionIdsSorted` | `expandPeaceTargetFactionIdsSorted` | `colonialPeaceTargetFactionIdsSorted` | `developPeaceTargetFactionIdsSorted` |

Given identical `(PhasePlanOutcome, regimentCount, hasInvadableProvinces)` inputs the resolver returns identical booleans across repeated calls (Refs #2509 Must-have #7).
- Given a `(Game, MapTopology, PlayerView, AIConfig, ...)` input set for one AI player turn and a `PhasePlanOutcome` distinguishable from `runPhasePlanners(planningGame, planningSnapshot, config.personalityId)` (for example a value-class instance carrying a different `phase` or fixture-populated slot content), when `runDomainPlannersWithOutcome(..., phasePlan: outcome)` runs, then every phase-derived call site inside the orchestrator (`_runEconomyDomainPlanners`, `runDiplomacyPlannerWithResult` invocations, `resolvePhaseConquestExtraPassesActive`, `runConquestArmyMovePlanner`, `runNavalPlanner`, and the late peace pass) consumes `outcome` directly — emitted orders match those produced when the same `outcome` is fed into the orchestrator via the internal dispatch path, and never reflect the alternate `runPhasePlanners` result that the orchestrator would have computed without the parameter. Given the same input set with `phasePlan: null` (the legacy entry shape), the orchestrator falls back to the internal `runPhasePlanners(...)` dispatch so existing orchestrator-level fixtures stay green during the S5 migration. The hoisted compute in `generateStrategicOrdersWithTrace` runs against the **planning-state** pair (`planningGame, planningSnapshot`) returned by `prepareConquestFieldArmy` / `AIWorldSnapshot.fromPlayerView` so the orchestrator sees the same dispatch inputs it would have used internally — eliminating the double-dispatch without changing the dispatch's `(Game, AIWorldSnapshot, personalityId)` keying.
- Given a `(Game, PlayerView, AIConfig, AISeedBundle, AIWorldSnapshot)` input set for one AI player turn placing the GP in the EXPAND below-quota peace treasury-recovery trap (`oldWorldProvincesOwned < kObserverConquestMinOwProvincesPerGp`, `regimentCount ∈ [1, kBelowQuotaPeaceMinRegimentsBeforeDeclareWar)`, `atWarWithAnyGreatPower == false`, `hasInvadableProvinces == true`, `treasury == 0`, empty stockpile), when `runEconomyPlanner(..., phasePlan: PhasePlanOutcome.defaultDevelop)` runs, then the resulting `EconomyPlan.cargoPreference` is strictly less than the preference returned by `runEconomyPlanner` against the same fixture with `phasePlan: null` (legacy compute path) or with `phasePlan: runPhasePlanners(game, snapshot, personalityId)` (natural-dispatch EXPAND path). The DEVELOP-injected planner must consume the supplied plan directly and suppress the recovery boost via `resolvePhaseEconomyExpandBelowQuotaPeaceZeroRegimentsRebuildActive` / `resolvePhaseEconomyExpandBelowQuotaPeaceInsufficientRegimentsActive` (both collapse to `false` under DEVELOP), never silently recomputing `isBelowQuotaPeaceTreasuryRecovery` from its canonical home in `expand_phase_planner.dart` (the helper was relocated there during S1 when `colonial_pressure.dart` was deleted).
- Given the same EXPAND-trap fixture and `phasePlan: runPhasePlanners(game, snapshot, personalityId)` against `phasePlan: null` (the legacy entry shape), when `runEconomyPlanner` runs both ways with identical `(Game, PlayerView, AIConfig, AISeedBundle, AIWorldSnapshot)` inputs, then `EconomyPlan.cargoPreference` is identical across both calls and `EconomyPlan.productionAssignments.length` matches. The phase-derived path (`resolvePhaseEconomyExpandBelowQuotaPeace*Active` resolvers + the treasury affordability arm `treasury + pendingRichesTreasuryDelta(stockpile) < cheapestRegimentBuildTreasuryCost()`) is field-equal to the legacy `isBelowQuotaPeaceTreasuryRecovery` compute under EXPAND / COLONIAL-lite because both phases require `oldWorldProvincesOwned < kObserverConquestMinOwProvincesPerGp` at entry via `observerGoalPhaseFor`, satisfying the legacy `isBelowObserverConquestQuota` guard structurally; any divergence here indicates the phase resolvers and the legacy compute have drifted apart on the rebuild-trap arms. The hoisted compute in `generateStrategicOrdersWithTrace` runs against the planning-state pair returned by `prepareConquestFieldArmy` / `AIWorldSnapshot.fromPlayerView` and is reused unchanged by `runDomainPlannersWithOutcome` (Refs single-dispatch contract above).
- Given identical `(Game, PlayerView, AIConfig, AISeedBundle, AIWorldSnapshot, PhasePlanOutcome)` inputs, when `runEconomyPlanner` runs twice in succession with the same hoisted `phasePlan`, then both invocations return field-equal `EconomyPlan.cargoPreference`, `EconomyPlan.productionAssignments.length`, and per-position `(recipeId, assignedLabour)` pairs (Refs #2509 Must-have #7). The phase resolvers read only `outcome.phase` and the regiment / war / invadable / treasury per-turn inputs, so any nondeterminism here would indicate the planner is reading state behind the parameter.
