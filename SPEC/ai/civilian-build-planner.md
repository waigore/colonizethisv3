# Civilian Build Planner

**SPEC/ai** — Derives from [civilian-units.md](../game/civilian-units.md) (types, costs, tech gates), [economy-planner.md](economy-planner.md) (recruitment/build emit order), and [order-suggestions.md](../program/order-suggestions.md) (candidate enumeration). Defines how the Full AI builds, replaces, and prioritizes civilian units (Explorer, Builder, Engineer, Spy, Merchant, Rail Builder).

---

## Problem

The AI deploys its starting civilians (2 Explorer, 2 Builder, 1 Engineer) but never issues a civilian `BuildUnitOrder`: lost civilians are never replaced and the workforce never expands.

## Goal

A deterministic, GA-tunable model that builds, replaces, and uses each civilian type, competing in the same weighted build pool as regiments/ships, gated by phase, per-type caps, tech, and a shared paper budget.

---

## Candidate enumeration (suggestion layer)

`suggestBuildOrders` ([order-suggestions.md](../program/order-suggestions.md) § Build orders) exposes civilian build candidates through an opt-in `includeCivilianBuilds` flag (default `false`). When enabled, it emits one `BuildUnitOrder` per `CivilianEconomyCatalog` type (`isMilitary: false`, `spawnProvinceId = capital`) that the order engine accepts, alongside regiment and ship candidates. The shared incremental candidate validator enforces **affordability** (treasury covers `buildTreasuryCost`, stockpile covers `buildInputs` paper, incl. pending riches), the **tech gate** (`unlockingTechByCivilianId`: Merchant ⇐ `merchant_companies`, Rail Builder ⇐ `early_steam_engine`; ungated types always buildable), and a **civilian capital spawn tile**. Ordering is deterministic (ascending `unitType`); when `false` the list is byte-identical to the military+naval-only list.

## Live economy wiring (enablement flag)

The live economy build pass (`domain_planner_orchestrator_economy.dart`) gates civilian build participation behind `kCivilianBuildPlannerEnabled` (default `false`), threaded through `PlannerContext.civilianBuildPlannerEnabled` exactly like `kGrowthStagePlannerEnabled`. When the flag is `false` the economy pass calls `suggestBuildOrders(..., includeCivilianBuilds: false)` and supplies no `CivilianBuildScoringInput`, so the candidate pool and `pickBuildOrder` scoring are byte-identical to the pre-#3793 military+naval path (no observer-determinism churn). When the flag is `true` the pass calls `suggestBuildOrders(..., includeCivilianBuilds: true)` and builds a `CivilianBuildScoringInput` from the active player's owned civilian unit counts (tallied from `PlannerContext.view.ownUnitsById` by `CivilianEconomyCatalog` type), the active phase name (`PhasePlanOutcome.phase.name`), and the Spy demand signal (`isAtWarWithAnyGreatPower` — war posture; the tech-steal posture is approximated by war demand until a dedicated signal lands). The recruitment planner keeps the default `false` (its `suggestBuildOrders` call only inspects candidates for the fabric-reservation check, which civilians never trigger). The deferred paper ledger (AC7) and research bias (AC6) remain deferred; per-candidate affordability and the max-cap ceiling already bound civilian builds when wiring is enabled.

## Scoring model (build pool)

Civilian candidates compete in the same `pickBuildOrder` weighted pool as regiments/ships. The civilian branch is **additive**: military/naval scores are unchanged for identical inputs. A civilian candidate score is:

```
base × phaseMultiplier[type] × minCapBoost × replacementUrgency × demandBoost
```

`pickBuildOrder` accepts an optional `CivilianBuildScoringInput` (owned count per type). When absent the civilian branch is inert (civilians keep the neutral `base` score; military/naval scoring is byte-identical to the pre-scoring path). When present:

- **Min cap (hard floor):** when `currentCount[type] < minCount[type]`, multiply by `kCivilianBuildMinCapScoreBoost` (a large elevation that dominates the military/naval bonus envelope).
- **Replacement urgency (soft pull):** while `minCount ≤ currentCount < targetCount`, multiply by `1 + replacementUrgencyFactor × (targetCount − currentCount)`; `1.0` when `currentCount ≥ targetCount`.
- **Max cap (ceiling):** a candidate at or above `maxCount[type]` is excluded from the pool before scoring (prevents over-building starving military/naval).
- **Phase multiplier:** `phaseMultiplier[type]` is read from `kCivilianBuildPhaseMultiplierByPhaseType` keyed by the active phase (`ObserverGoalPhase.name`, passed via `CivilianBuildScoringInput.phaseName`). EXPAND (and COLONIAL-lite) favor Builder; COLONIAL favors Explorer + Merchant; DEVELOP favors Engineer + Rail Builder (favored = `kCivilianBuildPhaseMultiplierFavored = 2.0`; all other type/phase pairs = base `1.0`). When `phaseName` is `null` every multiplier is the base, so the branch is phase-agnostic. Multipliers are **discrete per-phase** values; smooth `[0,1]` ramping (hysteresis via `phase_priority_weights.dart`) is deferred.
- **Spy (phase-flat + demand):** Spy uses `kCivilianBuildSpyPhaseFlatMultiplier` (identical across every phase — Spy never follows the economic phase model), plus `kCivilianBuildSpyDemandBoost` when `CivilianBuildScoringInput.spyDemand` is `true` (GP at war or pursuing a tech-steal posture). The Spy min floor is `kCivilianBuildMinSpies` (= `minCount[Spy]`, default `0`).

The scoring math lives in `ai_victory_config.dart` (`civilianBuildCandidateScore`, `civilianBuildPhaseMultiplier`, `isCivilianBuildAtOrAboveMaxCount`). `ObserverGoalPhase.name` ↔ `kCivilianBuildPhase*` key equality is locked by an `colonizethis_ai` contract test (`colonizethis_data` cannot import `colonizethis_ai`).

## Tech prioritization

The research planner prioritizes researching the **civilian-gating techs** that unlock civilian unit types (`merchant_companies` ⇒ Merchant, `early_steam_engine` ⇒ Rail Builder; the distinct values of `unlockingTechByCivilianId`) when the owning Great Power has not yet unlocked them, so the AI researches toward the gates that expand the civilian build pool. Concretely, in `runResearchPlannerWithDecision` the per-turn pool of new (non-in-progress) research-slot candidates is **stably reordered** so not-yet-unlocked civilian-gating candidates are selected first, with every other candidate keeping its original slot-index order. The reorder happens **within the unchanged per-turn slot target** — it adds no research slot and spends no extra funding — so it can never exceed the `researchPaperReserveShare` reservation. The bias is gated by the same enablement as the live civilian build pass (`PlannerContext.civilianBuildPlannerEnabled`, default `false`), so it is inert and observer-baseline-preserving until the live-wiring flag is flipped. The gating-tech set and the `isCivilianGatingTech` helper live in `ai_victory_config.dart` (no planner magic numbers; derived from `unlockingTechByCivilianId`).

## Paper budget (shared ledger)

Paper is shared across research, worker training, and civilian builds (design decision #11). `runRecruitmentPlanner` accepts an opt-in `paperBudgetLedgerEnabled` flag (default `false`). When enabled it **reserves research paper** up to `researchReservedPaper(currentPaper) = floor(currentPaper × kCivilianBuildResearchPaperReserveShare)` (default share `0.5`, GA-tunable in `[0.0, 1.0]`), subtracts paper already committed by pending orders in `currentOrders` (trained-worker recruits + civilian builds), and allocates the remaining `paperBudget` (floored at `0`) via the **same phase emit order** (DEVELOP: recruit/train first; EXPAND/COLONIAL/COLONIAL-lite: builds first) against a **running ledger**. Each accepted paper-costing candidate decrements the ledger; a candidate whose paper cost (trained-worker `materialCosts[paper]`, or — when `includeCivilianBuilds` is `true` — civilian `buildInputs[paper]`) would push the remainder below `0` is dropped with reason `kRecruitmentRejectPaperBudget`, leaving the budget for later candidates in emit order. The paper gate is evaluated **before** the peasant-reservation and soft-luxury-cap gates so the shared budget is the dominant constraint. When `paperBudgetLedgerEnabled` is `false` no paper checks run and the planner is byte-identical to the pre-#3793 path. The share and the integer-floor reservation math live in `ai_victory_config.dart` (`kCivilianBuildResearchPaperReserveShare`, `researchReservedPaper`); no planner magic numbers.

## GA-tunable parameters

Declared in `ai_victory_config.dart` (no planner magic numbers): per-type `minCount`/`maxCount`/`targetCount` maps, `kCivilianBuildBaseScore`, `kCivilianBuildMinCapScoreBoost`, `kCivilianBuildReplacementUrgencyFactor`, the per-phase multiplier map `kCivilianBuildPhaseMultiplierByPhaseType` (with `kCivilianBuildPhaseMultiplierBase` / `kCivilianBuildPhaseMultiplierFavored`), `kCivilianBuildSpyPhaseFlatMultiplier`, `kCivilianBuildSpyDemandBoost`, `kCivilianBuildMinSpies`, `kCivilianBuildResearchPaperReserveShare`, plus the deferred pool weight. Defaults: `minCount` Builder 2 / Explorer 1 / Engineer 1 / others 0; `targetCount` Explorer 2 / Builder 2 / Engineer 1 / others = `minCount`; `maxCount` Builder 6 / Explorer 4 / Engineer 4 / Spy 3 / Merchant 4 / Rail Builder 4; phase favored multiplier 2.0 / base 1.0; Spy phase-flat 1.0; Spy demand boost 2.0; research paper reserve share 0.5.

## Implemented vs deferred

- **Slice 1 (enumeration):** `includeCivilianBuilds` on `suggestBuildOrders`; AC1, AC1b, AC5, AC9, AC12.
- **Slice 2 (scoring caps):** additive civilian scoring branch in `pickBuildOrder` (min-cap floor, replacement urgency, max-cap exclusion) via optional `CivilianBuildScoringInput` + GA caps/constants; AC2, AC3, AC10, AC13, ACMax, AC8.
- **Slice 3 (phase multiplier + Spy demand):** discrete per-phase, per-type multipliers and the Spy phase-flat baseline + demand boost folded into `civilianBuildCandidateScore`, plumbed via `CivilianBuildScoringInput.phaseName` / `.spyDemand`; GA params added; `ObserverGoalPhase.name` key contract test; AC4, AC4b.
- **Slice 4 (live economy wiring):** `kCivilianBuildPlannerEnabled` flag + `PlannerContext.civilianBuildPlannerEnabled`; the economy build pass passes `includeCivilianBuilds` and a `CivilianBuildScoringInput` (owned counts / phase name / Spy demand) into `pickBuildOrder` when enabled, and is byte-identical to the prior path when disabled; ACWire1, ACWire2, ACWire3.
- **Slice 5 (research bias):** `runResearchPlannerWithDecision` front-loads not-yet-unlocked civilian-gating tech candidates (`kCivilianGatingTechIds` / `isCivilianGatingTech` in `ai_victory_config.dart`) within the unchanged per-turn slot target, gated by `PlannerContext.civilianBuildPlannerEnabled` (inert by default); AC6.
- **Slice 6 (shared paper ledger — this slice):** `runRecruitmentPlanner` opt-in `paperBudgetLedgerEnabled` / `includeCivilianBuilds` flags; reserves research paper (`kCivilianBuildResearchPaperReserveShare` / `researchReservedPaper`), then allocates the remainder via the phase emit order against a running ledger, dropping over-budget paper-costing candidates with `kRecruitmentRejectPaperBudget`; byte-identical to the prior path when disabled (default); AC7.
- **Deferred:** smooth `[0,1]` phase ramping (hysteresis) and a dedicated tech-steal posture signal (Spy demand currently uses war posture only).

## Acceptance criteria

- **AC1 (enumeration):** Given a Great Power with treasury ≥ 1000 and paper ≥ 2, when `suggestBuildOrders` runs with `includeCivilianBuilds: true`, then the returned list includes affordable, tech-unlocked civilian `BuildUnitOrder` candidates (Builder, Engineer, Explorer) alongside military/naval candidates, ordered deterministically by `unitType`.
- **AC1b (opt-out default):** Given the same player, when `suggestBuildOrders` runs with `includeCivilianBuilds` omitted (default `false`), then the returned list contains no civilian-type `BuildUnitOrder` and equals the military+naval-only list.
- **AC5 (tech gate):** Given a Great Power that has not unlocked `merchant_companies`, when `suggestBuildOrders` runs with `includeCivilianBuilds: true`, then the list contains no Merchant candidate; given `merchant_companies` unlocked and affordable, then the list contains a Merchant candidate.
- **AC9 (determinism):** Given identical `(Game, MapTopology, PlayerView, Orders)` and `includeCivilianBuilds: true`, when `suggestBuildOrders` runs twice, then both returned lists are identical in content and order.
- **AC12 (affordability floor):** Given a Great Power with treasury `0` or paper `< 2`, when `suggestBuildOrders` runs with `includeCivilianBuilds: true`, then the list contains no civilian `BuildUnitOrder`.
- **AC2 (scored, selectable):** Given a `Builder` civilian candidate and a regiment candidate with a `CivilianBuildScoringInput` whose `Builder` count equals `targetCount` (2), when `pickBuildOrder` runs, then `Builder` scores the neutral base `1.0` and is in the weighted pool (selectable, not guaranteed).
- **AC3 (min-cap hard floor):** Given a `Builder` count of `0` (below `minBuilders = 2`), when scored, then `civilianBuildCandidateScore('Builder', 0)` equals `kCivilianBuildBaseScore × kCivilianBuildMinCapScoreBoost` (50.0) — far above any military/naval score — and `pickBuildOrder` selects `Builder` over a regiment candidate.
- **AC13 (replacement urgency, distinct from min cap):** Given `minCount = 0`, `targetCount = 2`, when `civilianBuildCandidateScore` is evaluated at count `1`, then the result is `1 + kCivilianBuildReplacementUrgencyFactor × 1 = 1.5`; at count `≥ targetCount` the result is `1.0`.
- **ACMax (max-cap exclusion):** Given a `Builder` count at `maxCount` (6) and a candidate list of that `Builder` plus one regiment, when `pickBuildOrder` runs, then `Builder` is excluded and the regiment is selected.
- **AC10 (no regression — military/naval):** Given a military+naval-only candidate list, when `pickBuildOrder` runs with `CivilianBuildScoringInput` supplied versus omitted, then the selected order is identical.
- **AC8 (GA tunability):** When civilians are scored, the caps and scoring constants (including phase multipliers and the Spy demand boost) are read from `ai_victory_config.dart` (no civilian magic numbers in `build_planner.dart`).
- **AC4 (phase-dependent priority):** Given a non-Spy civilian type and `currentCount = targetCount` (replacement urgency neutral), when `civilianBuildCandidateScore` is evaluated with `phaseName`, then the score equals `kCivilianBuildBaseScore × phaseMultiplier`: in `expand` Builder = `2.0` while Explorer/Engineer/Rail Builder = `1.0`; in `colonial` Explorer = Merchant = `2.0` while Builder/Engineer = `1.0`; in `develop` Engineer = Rail Builder = `2.0` while Builder/Explorer = `1.0`. With `phaseName = null` every non-Spy type scores `1.0`.
- **AC4b (Spy phase-flat + demand):** Given a Spy with `currentCount ≥ targetCount` and `spyDemand = false`, when `civilianBuildCandidateScore` is evaluated for `phaseName` ∈ {`expand`, `colonial`, `develop`}, then the score is identical across all three phases (phase-flat, `kCivilianBuildSpyPhaseFlatMultiplier`). Given `spyDemand = true`, then the Spy score is multiplied by `kCivilianBuildSpyDemandBoost` on top of that phase-flat baseline, and this boost applies to no non-Spy type.
- **ACWire1 (disabled = inert):** Given `PlannerContext.civilianBuildPlannerEnabled` is `false` (the default), when the economy build pass runs, then `suggestBuildOrders` is called with `includeCivilianBuilds: false` and `BuildPickInput.civilianScoring` is `null`, so the build pool and selected order are identical to the pre-#3793 military+naval path.
- **ACWire2 (enabled, scoring input populated):** Given `PlannerContext.civilianBuildPlannerEnabled` is `true` and the active player owns `n` units of a civilian type, when `buildCivilianBuildScoringInput` runs, then it returns a non-null `CivilianBuildScoringInput` whose `currentCountByType[type]` equals `n` (types with zero owned units are absent), whose `phaseName` equals the active `ObserverGoalPhase.name`, and whose `spyDemand` equals the supplied war-posture signal.
- **ACWire3 (enabled, civilian buildable below min cap):** Given `PlannerContext.civilianBuildPlannerEnabled` is `true`, a Great Power below a civilian type's `minCount` with treasury and paper to afford it, and `suggestBuildOrders` emitting that civilian candidate, when the economy build pass runs, then a civilian `BuildUnitOrder` for that type can be appended (the min-cap hard floor lifts it into the weighted pool). Given the same state with the flag `false`, then no civilian `BuildUnitOrder` is appended.
- **AC6 (research bias — civilian-gating tech prioritized):** Given `PlannerContext.civilianBuildPlannerEnabled` is `true`, a Great Power that has **not** unlocked `merchant_companies`, and a research-slot candidate set containing both a non-gating tech (in a lower slot index) and the `merchant_companies` candidate (in a higher slot index) where only **one** new slot is funded this turn, when `runResearchPlannerWithDecision` runs, then the funded research order targets `merchant_companies` (the civilian-gating candidate is selected ahead of the non-gating candidate). The total number of funded slots is unchanged from the same scenario without the bias.
- **AC6b (research bias — negative, disabled/unlocked):** Given the same candidate set with `merchant_companies` placed in a higher slot index than a non-gating tech, when `PlannerContext.civilianBuildPlannerEnabled` is `false` (default), then the funded research order targets the lower-slot non-gating tech (no reordering). Given the flag is `true` but the Great Power has **already unlocked** every civilian-gating tech, then the candidate order is likewise unchanged (the bias selects no candidate to front-load).
- **AC7 (shared paper budget — reserve + ledger):** Given a Great Power holding `10` paper, `kCivilianBuildResearchPaperReserveShare = 0.5`, and trained-worker recruit candidates costing `5` paper each (journeyman), when `runRecruitmentPlanner` runs with `paperBudgetLedgerEnabled = true`, then the research reservation is `floor(10 × 0.5) = 5`, the allocatable budget is `5`, exactly one journeyman recruit is accepted (spend `5`, remainder `0`), and every subsequent paper-costing candidate is rejected with reason `kRecruitmentRejectPaperBudget`.
- **AC7b (shared paper budget — civilian builds compete):** Given a Great Power with `paperBudgetLedgerEnabled = true`, `includeCivilianBuilds = true`, an allocatable paper budget of `2` after reservation, and both a trained-worker recruit (cost `2` paper) and a civilian Builder build (cost `2` paper) on offer, when `runRecruitmentPlanner` runs in a phase whose emit order places the accepted candidate first, then exactly one of the two paper-costing candidates is accepted (spend `2`, remainder `0`) and the other is rejected with reason `kRecruitmentRejectPaperBudget`; the total paper committed never exceeds the allocatable budget.
- **AC7c (shared paper budget — disabled is inert):** Given the same state with `paperBudgetLedgerEnabled = false` (the default), when `runRecruitmentPlanner` runs, then no candidate is rejected with reason `kRecruitmentRejectPaperBudget` and the emitted recruit/build orders are identical to the pre-#3793 path (peasant-reservation and soft-luxury-cap behaviour unchanged).
