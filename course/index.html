The Phase List in Code — And Plain English

This enum defines every phase that runs each turn. Real code, exactly as in the game.

CODE 
enum TurnPhase {
  orders,
  extraction,
  richesToTreasury,
  production,
  consumption,
  research,
  diplomacy,
  movement,
  minorRegimentUpgrade,
  navalInterceptionCombat,
  combat,
  buildWork,
  endOfTurn,
}
PLAIN ENGLISH

orders — Players (human or AI) write what they want to do this turn

extraction — Mines and colonies pull raw gold ore from the map

richesToTreasury — Raw gold ore gets minted into spendable gold bars

production — Old World factories convert raw materials into goods

consumption — Colonies and armies eat food, depleting supplies

research — Universities generate research points for new technologies

diplomacy — Alliance and trade deal orders get processed

movement — All armies and fleets actually move on the map

minorRegimentUpgrade — Cheap army upgrades (muskets → rifles, etc.)

navalInterceptionCombat — Fleets try to intercept enemy fleets crossing the sea

combat — Land battles happen: forts fire, armies clash

buildWork — Colonies spend their production on buildings and units

endOfTurn — Turn number increases, the cycle restarts

💡
Key Insight

Notice the order is strict and always the same: extraction before production, because you need raw materials before you can refine them. You can't mint gold bars before the mines produce ore.

Three Design Pillars

The turn cycle works because of three non-negotiable rules built into every phase.

🔒

Immutability

No phase ever modifies the WorldState it receives. It reads, computes, and returns a new state. Like copying a document before editing — the original stays intact.

🧩

Phase Isolation

Each phase is completely standalone. If the extraction phase produces a bug, it cannot corrupt the combat phase. Problems stay contained to the phase that caused them.

🔁

Determinism

Same inputs in, same result out — every time. There are no dice rolls or random events inside phases. This is what makes replaying a turn and getting the same result possible.

💡
Why Does This Matter?

Imagine if phases could modify each other's state. A bug in consumption could silently corrupt your army positions. Immutability means you can always trace exactly what happened — and replay any turn step by step.

The PlayerView is how individual players see the world. Each player (human or AI) gets their own filtered view — they can't see enemy positions in fogged tiles, and they only see their own colony's interior.

CODE 
enum VisibilityLevel { unknown, revealed, fogged, fullyVisible }

class PlayerView {
  const PlayerView({
    required this.playerId,
    required this.player,
    required this.ownUnitsById,
    required this.provincesById,
    required this.visibilityByTile,
    required this.prospectedTiles,
    required this.diplomacyByOtherId,
  });

  VisibilityLevel visibilityForTile(String tileKey) =>
      visibilityByTile[tileKey] ?? VisibilityLevel.unknown;
PLAIN ENGLISH

Four levels of visibility — unknown (never seen), revealed (was seen, now dark), fogged (you know it exists but not what's inside), and fullyVisible (you can see everything).

PlayerView is the gatekeeper — every player (human or AI) gets their own version filtered to what they're allowed to see.

ownUnitsById — only the units this player controls, no enemy units.

visibilityByTile — a map of what this player can see in each tile on the map.

prospectedTiles — tiles where hidden resources (like gold veins) have been revealed.

The helper function — asks "what can this player see in this tile?" and returns unknown if the player has never looked there.

A deterministic decision engine that weighs goals against game state — no dice, no chaos, just math.

Screen 1 of 6

Not Magic — Math

The AI in ColonizeThis isn't magic. It's a deterministic decision engine that weighs goals against the game state. Give it the same inputs twice, and it makes the same decision every time.

🧠
The Methodical Employee

The AI is like a highly methodical employee with a secret notebook of hidden priorities. It generates decisions using a weighted goal system — calculating a score for every possible action and picking the highest. No randomness. No luck. Just math.

🎯
Goal Manager

Decides overall strategy — expand, defend, trade, conquer, research, or diplomacy first?

💰
Domain Planners

Three specialists: Economy Planner, Military Planner, Diplomatic Planner — each weights goals within their domain

⚔️
Tactical AI

Translates high-level goals into specific orders — where to move, what to attack, what to build

The AI Brain in Action

Watch how the AI's components "discuss" a decision — weighing competing goals and scoring every option.

GM
Goal Manager

Priority update: Expansion is our top goal this epoch. We need more provinces to outpace the rival empire.

EP

Understood. But expansion costs gold. I'm scoring every province by gold income minus garrison cost. Province NW-7 scores 0.73 — good return on investment.

TA

Combining your scores: 0.73 (economy) × 0.41 (military threat) = 0.30 final score. But Province S-3 scores 0.68 combined. I'm issuing orders for S-3.

GM
Goal Manager

Approved. Orders sent to TurnResolver. Next epoch — we reassess priorities based on the new game state.

?
💡
Weighted Scoring

Every possible action gets a score from 0.0 to 1.0. The AI multiplies domain scores together — a province with great gold but extreme military threat gets a low final score. This is why the AI sometimes ignores obvious opportunities: something else scored higher when all factors were combined.

Inside the AI Brain

The generateOrdersForPlayerFullAI function is the AI's "think" button. Here's what it actually does, line by line.

CODE 
StrategicOrderResult generateOrdersForPlayerFullAI(
  Game game,
  MapTopology topology,
  String playerId, {
  Map<String, TileMapResult>? tileMapByRegion,
  OrderSuggestionAPI? orderSuggestionApi,
  void Function(DialogueEvent)? onDialogue,
  void Function(PortraitMoodEvent)? onMood,
}) {
  final player = game.playerById(playerId);
  if (player == null || !isAiControlled(game, player.id)) {
    return const StrategicOrderResult(
      orders: Orders(),
      economyPlan: EconomyPlan(productionAssignments: [], cargoPreference: CargoPreference.none),
    );
  }
  final view = buildPlayerView(game, topology, playerId);
  return generateStrategicOrders(...);
}
PLAIN ENGLISH

The function signature — takes the current game state, the map layout, and which player to generate orders for. Optional callbacks let the AI trigger dialogue and portrait mood changes as it "thinks."

Look up the player — first it finds the player object by ID. If the ID is wrong or the player doesn't exist, it returns empty orders — this player gets no AI actions.

Is this an AI player? — double-checks that this player is actually AI-controlled (not a human). Humans give their own orders, so the AI skips them entirely.

Return empty if not AI — if either check fails, return a blank StrategicOrderResult with no orders and no economy plan. This player will rely entirely on human input.

Build the PlayerView — this is critical. The AI does NOT get the full game state. It gets a PlayerView — the same filtered view a human player would see. This enforces the fog of war on the AI too.

Delegate to strategic AI — the real thinking happens in generateStrategicOrders(), which applies goals, domain planners, and tactical scoring to produce actual order objects.

No Dice — Just Seeds

The AI uses seeding instead of randomness. Give the same inputs, get the same outputs. Every time.

🌱
Seed is set

Before the game starts, a seed number is chosen — either randomly or deliberately

→
🔢
Same seed = same sequence

The AI's "random" decisions are actually a deterministic sequence — but it looks unpredictable

→
🔁
Replayability

Give the same seed + game state = same AI decisions. Useful for replays and debugging

→
🎭
Personality without chaos

Different seeds give different AI personalities — aggressive, defensive, economic — all without dice rolls

💡
Seeding vs Randomness

Randomness means "this could be anything." Seeding means "this looks random but it's actually fixed — we just chose a complicated starting point." The AI doesn't flip a coin. It follows a recipe that produces different results depending on which seed was used. Both players with identical seeds and game states will make identical decisions.

Screen 5 of 6

Why Does the AI Use PlayerView?

The AI doesn't see the whole map. It sees exactly what a human player would see — and that's by design.

👁️
Fog of War for Everyone

The AI only knows what it has explored. Tiles in fog are unknown — the AI can't see enemy armies hiding there any more than a human could.

⚖️
Fairness by Architecture

If the AI used the full game state, it would effectively be cheating — knowing about armies the player can't see. PlayerView enforces equality.

🎯
Predicable AI

Because the AI works with the same limited information as the player, its decisions are predictable. Players can outmaneuver it by using fog strategically.

This is the same PlayerView you learned about in the Turn Ticker module. It's the gatekeeper for all game information — one version for the human UI, one for the AI.

The Merge Function, Line by Line

CODE 
/// Merges human and AI orders with
/// precedence (human over AI).
/// For conflicting orders (e.g. same unit,
/// same slot): human wins.
Orders mergeOrderLists({
  required Orders humanOrders,
  Orders? aiOrders,
}) {
  if (aiOrders == null ||
      _isEmpty(aiOrders)) {
    return humanOrders;
  }
  final merged = Orders(
    moveOrdersByPlayerId:
      _mergeMoveOrders(humanOrders...),
    armyMoveOrdersByPlayerId:
      _mergeArmyMoveOrders(...),
    // ... all 8 order types
  );
  return merged;
}

Map<String, List<MoveOrder>>
_mergeMoveOrders(...) =>
  _mergeByConflictKey(
    human, ai, (o) => o.unitId);
PLAIN ENGLISH

The function takes two order lists — yours and the AI's — and returns one merged list.

If there's no AI orders at all, just give back the human orders unchanged.

Otherwise, create a new merged Orders object by calling a helper for each order type.

For move orders, merge by unit ID — if two moves target the same unit, the human one wins.

The merge happens per-type, using a conflict key (like unitId) to spot collisions.
